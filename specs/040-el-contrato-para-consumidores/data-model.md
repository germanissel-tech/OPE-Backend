# Data model — fase 1 (040)

Lo que cambia de forma. Los tipos del contrato no se escriben: salen del bundle; acá se nombra qué
gana cada cosa.

## El operador, con nombre

```
OperatorRecord {
  operatorId: OperatorId
  tokenFingerprints: string[]        (1..2, hex de 64)
  scope: "*" | MerchantId[]
  displayName?: string               NUEVO · para mostrar; nunca un identificador
}
```

Reglas de `Operator.of`: las de siempre más `displayName`, si viene, **no vacío ni con espacios en
los bordes** y de hasta un largo máximo (nivel 0 de configuración: una constante nombrada del
dominio, como `MAX_TOKENS`). `rehydrate` no re-juzga. `Operator.system()` no tiene nombre.

Lo que lo lee: `AdminTokenResolver` (sin cambio: entrega el `Operator` entero), el caso de uso
`GetOperatorUseCase` (lo devuelve) y el presentador `operatorDto`. **Lo que no lo lee**: el registro de
administración (`AdminEntry.operatorId` sigue siendo la única identidad) y cualquier otro consumidor.

Configuración (`operators-config.ts`, `config/schemas/operators.schema.json`): `displayName` opcional,
`type: string`, `minLength: 1`; cualquier otra propiedad sigue rechazada (`additionalProperties:
false`). `config/dev-operators.json`: `dev-operator` gana `"displayName": "Operador de desarrollo"`.

## La respuesta de `getOperator`

```
Operator (esquema del contrato, components/schemas/Operator.yaml)
  operatorId: OperatorId           required
  displayName?: string             la única propiedad con nombre de persona del contrato (R-05)
  scope: "*" | MerchantId[]        required · la misma forma que la configuración
```

`GET /v1/admin/operator` · tag `admin` · `security: adminToken` · `x-required-capabilities: []` ·
`x-identifies-principal: true` · respuestas `200` (`Operator`), `401` (`OperatorUnauthorized`), `500`.
Sin `403`: no hay merchant ni capacidad que negar. Sin `x-collection`, sin `x-idempotency` (es una
lectura).

## El Problem Details, con identificador

```
ProblemDetails
  type, title, status            required (sin cambio)
  detail?, instance?             (sin cambio)
  errors?: [{ pointer, message }] (sin cambio de forma; `pointer` ahora siempre relativo al pedido)
  requestId?: string             NUEVO · el identificador del pedido, igual al encabezado X-Request-Id
```

`requestId` lo pone el transporte (`send()`), no el controller. `X-Request-Id` va en **toda**
respuesta, problema o no.

## El invariante, con campo

```
x-invariants[]
  type, status, rule, description   (sin cambio)
  pointer?: string                   NUEVO · sólo en invariantes de esquema · camino relativo al cuerpo,
                                     `origins[N]` para «el elemento N», `graceSeconds` para un campo
```

Lo publica el servidor como `/body/` + camino con `N` resuelto (`/body/origins/1`). Lo declaran, en
esta feature: `invalid-origin` (`origins[N]`), `origin-already-registered` (`origins[N]`),
`rotation-grace-too-long` (`graceSeconds`), `configuration-reason-required` (`reason`, que ya lo
publicaba sin `/body`). Los demás invariantes de esquema que señalan un elemento se declaran si el
error de dominio ya sabe cuál (R-01) y quedan anotados si no.

## El error de dominio, con puntero

`DomainError.details` ya admite `pointer` (escalar). Convención: el camino desde la raíz del cuerpo,
en notación `a.b[2].c`, que `toProblem` traduce y **prefija con `/body`**. Ganan puntero:
`OriginAlreadyRegistered(index)` → `origins[${index}]`; `InvalidOrigin(index)` → ídem;
`RotationGraceTooLong(maxGraceMs)` → `graceSeconds`.

## Los artefactos para consumidores

```
generated/contract/
  openapi.yaml           copia byte a byte del bundle
  api.d.ts               copia de generated/api.d.ts
  problem-types.d.ts     copia de generated/problem-types.d.ts
  capabilities.js        CONTRACT { version, sha256 } · CONSUMER 'admin' · CAPABILITIES (unión ordenada)
                         · OPERATIONS { <operationId>: { capabilities: [...], idempotent } } en el orden del bundle
  capabilities.d.ts      los tipos de arriba: CAPABILITIES como tupla literal, Capability, OperationId
  constraints.js         CONTRACT · CONSTRAINTS { <Schema>: { required, fields } } ordenado por nombre
  constraints.d.ts       FieldConstraints, MessageConstraints, CONSTRAINTS con una clave por esquema, ConstrainedSchema
  identity.json          { "$comment", "version", "sha256" }   (sin commit: determinista)
```

Cada archivo con la cabecera `GENERATED by scripts/contract-consumer-artifacts-lib.mjs — DO NOT EDIT
BY HAND. Regenerate with: npm run contract:types`. La forma exacta de cada uno es la de
`specs/005-la-base-de-ope/contracts/contract-artifact.md` y
`specs/006-el-merchant-completo/contracts/constraints-artifact.md` de OPE-Web, reproducidas en
[`contracts/consumer-artifacts.md`](contracts/consumer-artifacts.md) de esta feature.

**Qué esquemas entran a `CONSTRAINTS`**: todo `components.schemas.<Name>` con `type: object` que algún
`requestBody` de una operación `admin` referencie por `$ref`, y los que ésos referencien (propiedad
`$ref` o `items.$ref`), recursivamente. **Qué se lee de cada propiedad**: `type`, `minLength`,
`maxLength`, `pattern`, `minimum`, `maximum`, `minItems`, `maxItems`, `items` (recursivo), `enum`,
`format`; un `$ref` a esquema → `{ type: 'object', ref: '<Name>' }`. Ni `default` ni `description`.

## Estados y transiciones

No hay máquina nueva. Lo que cambia de estado es el mapa del contrato: `getOperator` nace `built`
con `feature: "040"` (no pasó por `planned` porque la decisión de construirla y la construcción son
